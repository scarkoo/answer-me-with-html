# Answer me with HTML — 복잡한 답변을 한 페이지로 설명하기

기본적으로 모델은 **내용 원고(확장 Markdown)**만 작성한다. 레이아웃, 색상, 다크 모드, 다이어그램 좌표는 `am` CLI가 처리한다. **HTML / CSS / SVG를 직접 작성하는 것은 내장 컴포넌트로 표현할 수 없거나 인터랙션이 필요한 경우의 escape hatch로만 사용한다.**

## 0. 사용자가 설정을 바꾸려는 경우

설정 변경 요청에서는 페이지를 만들지 말고 설정만 처리한다.

- 현재 설정 확인: `node "$AM" config`
- 값 변경: `node "$AM" config set <key> <value>`
- 특정 값 초기화: `node "$AM" config reset <key>`
- 전체 초기화: `node "$AM" config reset`

사용자가 자연어로 요청해도 같은 의미의 명령으로 변환한다.

예:
- "브라우저 자동으로 열지 마" → `config set open off`
- "기본 테마를 카드로 바꿔" → `config set theme shadcn`
- "STE 검사 끄자" → `config set style off`

주요 설정:
- `open`: 생성 후 브라우저 자동 열기. 이 Codex fork의 기본값은 `off`.
- `always`: 고빈도 모드용 설정. Codex에서는 이 값만으로 자동 동작하지 않으며 AGENTS.md 같은 전역 규칙과 함께 써야 한다.
- `theme`: `blueprint | shadcn`
- `mode`: `auto | light | dark`
- `style`: `off | 80 | strict`

## 1. 판단: 페이지를 만들 것인가

다음 중 하나라도 만족하면 페이지를 만든다.

- 서로 연관된 개념이 3개 이상이고 관계를 한눈에 보는 것이 도움이 된다.
- 프로세스, 프로토콜, 호출 체인, 상태 전이처럼 흐름이 있다. 특히 분기나 여러 참여자가 있으면 우선 사용한다.
- 3개 이상의 기준으로 비교하거나 여러 선택지의 trade-off를 설명한다.
- 디렉터리, 모듈, 분류 체계 같은 계층 구조가 있다.
- 역사, 릴리스, 프로젝트 단계처럼 시간에 따른 변화가 있다.

만족하지 않으면 일반 텍스트로 답한다. 애매하면 "그림으로 보면 더 빨리 이해되는가?"를 기준으로 판단한다.

### 고빈도 모드

Codex에서 고빈도 모드를 원하면 전역 `AGENTS.md` 같은 규칙 파일에 "결론, 요약, 계획, 비교, 리뷰, 설명이 있는 응답에는 answer-me-with-html 페이지를 함께 만든다"는 규칙을 둘 수 있다.

고빈도 모드에서는:

- 답변에 결론, 요약, 계획, 비교, 리뷰 또는 설명이 있으면 짧더라도 페이지를 함께 만든다.
- 일상적인 답변은 2~4개 패널로 작게 구성한다. 결론 `callout` 하나와 표 또는 그림 하나면 충분할 수 있다.
- 패널 수를 채우기 위해 의미 없는 내용을 추가하지 않는다.
- 기본적으로 `--no-open`으로 렌더링한다.
- 최종 답변에는 텍스트 결론을 먼저 주고 마지막에 생성된 페이지 경로를 남긴다.
- 잡담, 결론 없는 1~2문장, 순수 명령 출력, 사용자가 plain text를 요구한 경우에는 만들지 않는다.

## 2. 작업 흐름 — 한 번의 CLI 호출로 렌더링

CLI는 skill 폴더의 `scripts/am.mjs`에 단일 파일로 번들되어 있다. Node.js 20+만 필요하며 별도의 `npm install`은 필요 없다.

Codex의 기본 전역 설치 경로:

```bash
AM="${CODEX_HOME:-$HOME/.codex}/skills/answer-me-with-html/scripts/am.mjs"
```

해당 경로에 없으면 **현재 로드한 이 SKILL.md가 있는 디렉터리를 기준으로 `scripts/am.mjs`의 절대 경로를 찾는다.** 현재 프로젝트의 working directory가 skill 디렉터리라고 가정하지 않는다.

1. 먼저 3~8개의 패널을 머릿속에서 구성한다. 각 패널은 하나의 하위 질문만 답한다.
2. 정보 형태에 맞는 컴포넌트를 선택한다. 아래 4절을 우선 참고한다.
3. heredoc으로 한 번에 렌더링한다.

````bash
node "$AM" render - --no-open <<'AM_EOF'
---
title: 제목
---
## A 패널 제목
```flow
A -> B: 라벨
```
AM_EOF
````

4. CLI 출력을 읽고 처리한다.
   - `✓ <path>`: 성공. 생성된 페이지 경로를 최종 답변에 남긴다.
   - `✗ L<line> [component] ...` + 올바른 예시: 해당 줄을 예시에 맞게 고친 뒤 다시 렌더링한다.
   - `STE n warnings`: 가능한 경우 경고에 맞춰 문장을 고치고 다시 렌더링한다.
5. 오류나 STE 경고 수정은 최대 2회까지만 재시도한다. 그래도 경고가 남으면 페이지는 유지하고 필요한 경우 경고가 남았다고 짧게 알린다.
6. 사용자가 명시적으로 브라우저 열기를 원한 경우에만 `--open`을 사용한다.

## 3. 원고 형식 빠른 참조

````markdown
---
template: sheet     # sheet = 패널 그리드(기본, 한 화면 총람) | doc = 한 열의 선형 설명(순차적으로 읽기)
theme: blueprint    # blueprint = 도면 스타일(기본) | shadcn = 깔끔한 카드 스타일
title: 페이지 제목
subtitle: 한 줄 설명     # 선택
cols: 3             # sheet의 열 수, 기본 3. 각 패널은 span / rows로 가로·세로 크기를 조절
style: 80           # STE 검사: off | 80(기본, 경고만) | strict(경고가 있으면 렌더링 거부)
mode: auto          # auto = 시스템 설정 따름 | light | dark
source: RFC 9293    # 예약 키가 아닌 다른 frontmatter 값은 페이지 헤더의 메타 정보로 표시
---
도입부: 핵심 결론을 한두 문장으로 작성한다. # 선택

## A 패널 제목 {span=2 meta="오른쪽 위의 작은 설명"}
일반 Markdown을 사용한다: 문단, 목록, 표, 인용, inline code.
표 셀의 상태 단어: ok / no / warn
상태 뒤에 텍스트를 붙일 수도 있다: "ok 승인됨" → ✓ 승인됨

## B {bare}         # bare = 패널 제목 바 제거. kv 형태의 title block 등에 적합
````

- 패널의 알파벳 ID는 생략할 수 있다. 생략하면 A, B, C... 순서로 자동 할당한다.
- `span=2`는 패널을 두 열 너비로 만든다. `rows=2`는 두 행 높이로 만든다.
- `html` / `svg` fenced block은 원본 마크업으로 삽입된다. **내장 컴포넌트로 표현하기 어렵거나 사용자 인터랙션이 필요할 때만 사용한다.**
- 전체 원고 문법: `node "$AM" help format`
- 컴포넌트 문법: `node "$AM" help <component>`
- 컴포넌트 목록: `node "$AM" list`

## 4. 정보 형태에 따라 컴포넌트 선택

| 정보 형태 | 컴포넌트 | 최소 문법 |
|---|---|---|
| 무엇이 무엇으로 연결되는가, 아키텍처, 호출 체인, 의사결정 분기 | `flow [LR]` | `A -> B: 라벨`, `A --> C` 점선, `A -> B & C` fan-out, `{판단?}`, `(시작)`, `[(DB)]`, `*중요`, `group 이름: A, B` |
| 여러 참여자 사이에서 시간 순서로 오가는 메시지 | `sequence [num]` | `A -> B: 요청`, `B --> A: 응답`, `note A, B: 설명`, `== 단계 ==` |
| 디렉터리, 모듈, 분류 같은 계층 구조 | `tree [list]` | 들여쓰기로 계층 표현, `라벨 \| 설명`, `` `번호` 라벨 `` |
| 역사, 릴리스, 프로젝트 단계 | `timeline [v]` | `시간 \| 제목 \| 설명`, 앞에 `*`를 붙여 강조 |
| 값과 상한/한계 비교 | `limits` | `라벨 \| 13 / 20 \| 단위`, 상한만 있으면 `라벨 \| max 20` |
| 문장이나 코드 조각의 부분별 주석 | `annot` | `# 작은 제목 \| 오른쪽 메타`, `[구간]{주석}`, `[문제]{!빨간 주석}`, `> 하단 설명` |
| 메타데이터 / 도면 title block | `kv [cols=2]` | `키: 값`, `* 넓은 셀: 값` |
| 결론, 팁, 경고, 오류 | `callout <info\|ok\|warn\|err> 제목` | 본문은 일반 Markdown |
| 여러 항목의 다차원 비교, 가능/불가능 체크 | Markdown 표 | 상태 셀에 `ok / no / warn` 사용 |

선택 원칙:

- **결론부터 배치한다.** 첫 패널 또는 도입부에 핵심 답을 쓰고 나머지 패널에 근거를 배치한다.
- 패널 하나는 질문 하나만 답한다.
- 8개를 넘기면 페이지를 나누거나 덜 중요한 패널을 제거한다.
- 정보량이 많은 패널은 `span`으로 더 넓게 잡는다.
- `annot`처럼 일정 폭이 필요한 내용은 최소 `span=2`를 우선 고려한다.
- 데이터를 만들어내지 않는다. 실제 숫자가 없으면 `limits`를 억지로 쓰지 않는다.
- 예시 숫자를 사용할 때는 페이지 안에서 "예시" 또는 "illustrative"라고 명시한다.

## 5. HTML / SVG / JavaScript 인터랙션과 CSP

내장 컴포넌트로 표현하기 어려운 UI, 자유형 시각화, 사용자 인터랙션이 필요하면 raw HTML/SVG를 사용할 수 있다.

- Markdown 내부 raw HTML과 `html` / `svg` fenced block은 그대로 렌더링된다.
- inline `<script>`, `onclick` 같은 이벤트 핸들러, `javascript:` 링크를 사용할 수 있다.
- 이런 기능은 **로컬 페이지 인터랙션**에 사용한다. 예: 탭 전환, 접기/펼치기, 필터, 로컬 계산, 시각 상태 변경.
- 생성 페이지 CSP는 `connect-src 'none'`으로 `fetch`, XHR, WebSocket 같은 직접 네트워크 연결을 막는다.
- 외부 script, object, iframe/frame, media, worker, manifest는 차단한다.
- inline CSS/JavaScript는 허용한다.
- 외부 HTTPS font 파일과 data URI font는 허용한다(`font-src https: data:`).
- 외부 stylesheet 자체는 허용하지 않는다. 필요한 외부 폰트는 inline `@font-face`에서 HTTPS font 파일을 직접 참조한다.
- `base-uri 'none'`, `form-action 'none'`, `referrer=no-referrer`를 유지한다.
- CSP가 모든 브라우저의 top-level navigation까지 완전히 차단한다고 가정하지 않는다. 사용자 데이터, 프로젝트 경로, 소스 코드 등 민감할 수 있는 내용을 외부 URL query/hash에 넣어 이동시키지 않는다.

## 6. STE controlled writing — 원고의 문장 품질

`am render`는 원고를 렌더링하기 전에 ASD-STE100에서 가져온 일부 원칙을 자동 검사한다.

STE(Simple Technical English)는 기술 문서를 더 빠르고 일관되게 읽게 하기 위한 controlled language 접근이다. 이 skill은 그중 기계적으로 검사할 수 있는 규칙을 영어와 중국어에 적용한다. 한국어 원고에서는 모든 규칙이 동일하게 적용되지는 않지만, **짧은 문장·한 문장 한 의미·일관된 용어·직접적인 문체** 원칙은 그대로 따른다.

검사 수준:

- `style: 80`: 기본값. 경고를 출력하지만 페이지는 생성한다.
- `style: strict`: 경고가 하나라도 있으면 페이지 생성을 거부한다.
- `style: off`: STE 검사를 끈다.

작성 규칙:

- **한 문장에는 한 가지 내용만 쓴다.**
- 가능한 한 능동태를 쓴다.
- 절차 단계는 명령형/직접적인 동사로 시작한다. "밸브가 닫혀야 한다"보다 "밸브를 닫는다"가 낫다.
- 같은 개념은 페이지 전체에서 같은 용어로 부른다. 한 단어에 여러 의미를 섞지 않는다.
- 절차 단계(ordered list)의 길이 상한:
  - 영어: 20 words
  - 중국어: 35 characters
- 일반 설명 문장의 길이 상한:
  - 영어: 25 words
  - 중국어: 45 characters
- 한 문단은 최대 6문장으로 제한한다. 더 길면 목록이나 별도 패널로 나눈다.
- 영어에서는 흔하고 짧은 단어를 선호한다.
  - `use` — `utilize` 대신
  - `start` — `commence` 대신
  - `before` — `prior to` 대신
- 중국어에서는 불필요한 허동사를 줄인다.
  - `进行优化` → `优化`
  - `加以说明` → `说明`
- 중국어에서 한 문장에 `的`가 3번 이상 연속적으로 반복되는 구조를 피한다.
- 상투어와 추상적인 표현을 피한다. `赋能`, `闭环`, `至关重要` 같은 말 대신 구체적인 사실을 쓴다.
- 일부러 보여주는 잘못된 예시는 `~~취소선~~`으로 쓰거나 상태가 `no`인 표 행에 넣는다. STE 검사는 이런 반례를 건너뛴다.
